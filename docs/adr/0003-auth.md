# ADR-0003 — Authentication via OIDC against OPERAS ID

**Status:** Accepted

**Date:** 2026-05-17

## Context

The CMDB needs to know who is editing. v1 is single-namespace (`edch`) and single-tenant from an authorisation standpoint — if you can sign in, you can see and edit the EDCH inventory. Fine-grained per-namespace or per-action authorisation is a v2 problem (ADR will be filed when it lands).

OPERAS ID is the natural identity source for OPERAS / EDCH operations (ADR-0001 already named it). Local accounts would be a maintenance burden and a separate password to forget. Federating through OPERAS ID also gives us a clean session-revocation story (revoke at the IdP, sessions die at next refresh).

The CMDB does not need long-lived refresh tokens or offline access. Short-lived sessions, re-authenticate when they expire.

## Decision

| Concern | Choice |
| --- | --- |
| Protocol | OpenID Connect — Authorization Code + PKCE |
| Library | [`openid-client`](https://github.com/panva/openid-client) (v6, ESM, no transitive deps) |
| Identity provider | OPERAS ID |
| Session storage | HMAC-signed cookie holding the ID token claims (no DB hop on every request) |
| Session lifetime | 12 hours — short enough that IdP-side revocation propagates within a working session |
| Cookie posture | `HttpOnly`, `SameSite=Lax`, `Secure` when not localhost, signed with `SESSION_SECRET` |
| Route protection | Single Astro middleware (`src/middleware.ts`) — every route except `/auth/*` requires a session |
| Logout | Local session clear, then RP-initiated logout against OPERAS ID when `end_session_endpoint` is advertised |
| Dev / test escape hatch | `AUTH_MODE=dev` env binds a fixed dev user, skips the OIDC flow — for stack-up testing without OPERAS ID registered yet |

## Why not …

- **Astro experimental session API:** filesystem-backed by default, scales badly to multi-instance, less control over claims layout. Signed-cookie sessions are 30 LOC and explicit.
- **Refresh tokens / silent renewal:** unnecessary at this scope; 12h sessions and a re-login on expiry are fine.
- **Local accounts (passport-local, etc.):** the maintenance burden defeats the point of federation.

## Authorisation in v1

The middleware enforces "must be signed in to do anything", nothing more. Claims attached to the session:

- `sub` — OIDC subject (stable IdP-assigned identifier)
- `email`
- `name`
- `groups` — passed through if OPERAS ID advertises them, used by v2 for per-namespace mapping

For v1 every signed-in user can read and write every EDCH-namespace asset. Audit log captures `actor` from `sub` (or `email` if `sub` is opaque), so every change is attributable even in the permissive v1 model.

## Authorisation in v2 (planned, not implemented)

When OPERAS becomes a sibling namespace, the model gains:

- A `permission` table mapping `(sub, namespace, role)` triples
- A per-row authorisation check that requires the session's namespace allowlist to include the row's namespace
- A default role hierarchy: `readonly < admin < owner`
- A bootstrap path: the first OPERAS sysadmin's `sub` lands in `permission` via a seed migration

OPERAS ID's `groups` claim is the upstream source — if `groups` contains `cmdb-edch-admin`, the session gets `(edch, admin)` automatically. The local `permission` table is the fallback for cases where the group mapping is not yet in place.

## AUTH_MODE=dev

When `AUTH_MODE=dev`:

- The middleware short-circuits and injects a hardcoded session: `sub=dev`, `email=dev@local`, `name=Dev`, `groups=[]`
- `/auth/login`, `/auth/callback`, `/auth/logout` all return 404
- The Base layout shows a red "DEV AUTH — NO PRODUCTION USE" banner

The intent is exactly: spin up the docker compose stack, navigate to `http://127.0.0.1:4321`, and see the empty tables without registering an OIDC client first.

`AUTH_MODE` defaults to `oidc`. Production deployments MUST leave the default in place; the dev-mode banner makes any leak obvious during smoke-testing.

## Consequences

**Positive:**

- One IdP, no password management.
- Session cookies are self-contained, no DB round-trip per request, no shared session store between app instances.
- The dev escape hatch unblocks local testing before OPERAS ID has the client registered.

**Negative:**

- IdP-side revocation only takes effect at session expiry (max 12h). Acceptable for v1; if a sharper revocation is required later we can introduce a per-session DB record with revocation flags.
- `openid-client` v6 is ESM-only; we are ESM-only anyway, so this is just a footnote.

## Notes

- `SESSION_SECRET` must be at least 32 bytes (HS256 wants ≥ 256 bits of secret).
- The dev-mode banner is a deliberate eyesore; do not stylise it away in production CSS.
- The audit log records `actor` as the OIDC `sub` first, falling back to `email` only when `sub` is opaque. Reviewing audit history with two different keys for the same user is the lesser evil compared to losing the stable identifier.
